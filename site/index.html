An experiment in model acceleration

Exactuary

AI coding agents can now rewrite actuarial models as fast, low-level code. We tested how far that goes on ordinary processors, without GPUs, and how mathematical proof can show that the optimised models match the originals. The test used four open source life insurance models from lifelib.

  • Compilation and parallel cores ran a savings model about 420 times as fast as lifelib's version on one desktop computer, with identical results.
  • Early exit took this to about 870 times, with a mathematical proof that the results are unaffected.
  • Two programs back the proofs: Z3 found them, and Lean, the proof checker mathematicians use, checked the main statements again.

Background

Actuarial cashflow models

Life insurers use actuarial cashflow models to estimate what their policies will pay out and bring in over many years. The model takes each policy, such as a savings plan or a life cover, and projects its premiums, claims, surrenders, and expenses month by month. It then discounts these future cashflows to a single value today.

Insurers use the results to set reserves, price new products, report under rules such as Solvency II and IFRS 17, and work out how much capital to hold. A full run covers every policy, often under hundreds or thousands of economic scenarios. Many teams write these models in Python or in specialist actuarial software.

The four models in this experiment

Savings

A savings policy with an account value, investment returns, fees, and guaranteed death and maturity benefits.

Savings with dynamic lapses

The same product, but more people cancel when the guarantee is worth little.

Term assurance

Life cover for a fixed term, with monthly premiums.

Traditional life, annual

Term, whole life, and endowment policies, with reserves and cash values, projected year by year.

All four come from lifelib, an open source library of actuarial models written in Python. They are simpler than production models, but they use the same kinds of calculation.

This slide sets the scene for readers outside actuarial work. Everything later in the deck applies to these four models.

The question

Purpose

Why speed is wanted
  • Some calculations run a full set of scenarios inside every scenario of another set. 1,000 scenarios inside each of 1,000 scenarios means one million projections.
  • More scenarios reduce the sampling uncertainty in an estimate such as a 1-in-200-year loss.
  • Teams can answer pricing and planning questions in seconds.
  • Existing runs cost less to compute.
Why trust is the hard part
  • Teams validate and approve their models. A faster model is a different program, so it's not covered by the existing validation.
  • Matching final results is weak evidence. In our tests we compared the present values on a sample portfolio, both in total and for each policy. That missed 27% to 42% of deliberately planted errors. Comparing every value in every month caught 95% to 99%.
  • Some ways of going faster change the order or the precision of the arithmetic. This adds small rounding differences, or numerical noise, so the results no longer match exactly. We then need a guaranteed limit on how far rounding can move each result.
  • Some platforms now let insurers run analyst-readable code, such as Python or R, on GPUs. That gives some speed. In our tests a GPU also brought rounding differences, extra checks, and a queue for hardware.
  • AI coding agents can now rewrite a model as low-level code quickly. That opens another route: compile the model and run it on ordinary processor cores.
  • Mathematical proofs that the new code equals the original can then support model validation.

An optimised model needs proof that it matches the model it replaces.

The approach

Two ways to make a model faster

Starting point · Level 1The model as lifelib supplies it, which works out all policies together, one month at a time.
1

Optimised code

An AI coding agent rewrites the model by following a set conversion procedure. An automated pipeline then compiles it to machine code, spreads it across all processor cores, and checks it against the original.

Level 2

Compilation

Compiled to machine code, running one policy at a time on one core.

Level 3

Parallel cores

All the processor cores share the policies between them.

Level 4

Early exit

Each projection stops once nothing is left in force, and some sums are rearranged.

2

Accelerator chips

Move the calculation to a graphics processor (GPU), which does thousands of simple sums at once.

Level 5

Move to a GPU

The same calculation on a graphics processor, at the normal precision of about 16 digits.

Level 6

Reduce GPU precision

About seven digits instead of 16, which graphics processors handle many times faster.

For each level we set out the optimisations we make and how we demonstrate that the results are unaffected, or how little they change.

Each level builds on the one before. Compilation and parallel cores keep the arithmetic exactly as it was. Early exit and the GPU change it, which is where proofs and rounding bounds come in.

  • Most of the gain comes from compilation and parallel cores on an ordinary processor: about 106 to 424 times as fast as lifelib's version for the three monthly models.
  • Early exit roughly doubled the speed again for three of the four models, and added nothing for the dynamic lapse model.
  • None of these tasks needs a GPU. With parallel cores and early exit, one desktop computer projects a billion rows of the savings model in about five minutes, without the cost or limited supply of GPUs.

01 · What a cashflow model does

Projecting one policy

A projection follows a policy forward one month at a time. Each month it works out how many policies are still in force. It then works out the cashflows: premiums coming in, and claims, surrenders, and expenses going out.

Each month starts where the last one finished. The policies in force at the start of month 13 are those left at the end of month 12. This chain makes projections hard to speed up, and it comes up again later.

Finally, the model discounts the cashflows and adds them up. This gives a present value: one number for each policy in each scenario.

02 · Where the time goes

What can run in parallel

Across policies and scenarios

Independent policies

In the example models, policies do not affect each other, so a computer can work on one million of them at once. Parallel cores and GPUs rely on this.

Across months

Sequential periods

Month 13 needs the policies in force and the account value at the end of month 12. However you arrange the work, each policy's months come one after another.

Inside one month

Calculations within a period

A computer can work out premiums and claims for the same month side by side. There are only a few dozen such amounts, which cannot keep thousands of processors busy.

  • Vectorising, common advice for Python models, works out one month for all policies, then the next month.
  • lifelib's versions also keep every month's values in memory, and keep calculating policies that have already matured.
  • Compilation turns this round: each policy runs through all its months as machine code, passing a few values from one month to the next.

04 · Is it still the same model?

How we show that the results are unaffected

A faster model is a new program. Before anyone relies on it, they need evidence that it gives the same results as the original. We used three kinds.

1
Test: compare every value

We ran the original and the fast model on test portfolios and compared 1.6 billion values, month by month. None differed. We also planted errors on purpose, to measure how many the comparison catches.

Every step
2
Prove: show the two models are equal for every policy

A program called Z3 found a mathematical proof for each formula. A second program called Lean then checked the main statements again. Lean is the proof checker mathematicians use for research.

Matters most from early exit onwards
3
Bound: limit the effect of rounding

Computers round numbers. For each row in a checking run, we worked out a guaranteed limit on how far rounding can move each result.

Early exit and GPU
  • Tests cover only the policies tested. They always leave the question "did we test enough?", which is hard for a model validation team to settle.
  • A proof covers every policy, so that question does not arise for the calculations it covers. We rely on proofs wherever an optimisation changes the arithmetic.

Section 04 covers testing, section 05 covers proof, and section 06 covers rounding.

04 · An illustration, not from our models

The difference between a test and a proof

Testing
Is 3 × (4 + 5) = 3 × 4 + 3 × 5 ?
27 = 27 ✓a = 2, b = 7, c = 1 ✓a = −1, b = 0.5, c = 8 ✓

Each check convinces you about that case. No number of checks covers every case.

Proof
a × (b + c) = a × b + a × c
for every number a, b, and c

The rules of arithmetic establish this for all numbers, including ones nobody has tried.

The same idea works for models. A test runs the original and the fast model on chosen policies and compares the numbers. A proof works on symbols, such as "the policy's age" and "the sum assured", and shows that the two models give the same formula for every policy.

04 · Testing · Our results

Why we compare every value, not only totals

To measure how good a check is, we planted errors in the fast model on purpose, one at a time: a plus instead of a minus, a wrong constant, the wrong row of a table. We then counted how many each check caught.

  • Comparing portfolio totals, or each policy's present values, caught only 58% to 73%. Some errors cancel out. Others change amounts that the totals never use.
  • Comparing every value in every month caught 95% to 99%. A difference in one value also shows which calculation went wrong.
  • For most of the rest, the proofs either find a difference or show that the change makes no difference.

How to read the chart: each bar is the share of planted errors that one check caught. A longer bar means a better check.

04 · Testing

What comparison tests cannot show

These limits apply to any test that compares two models on chosen policies, including ours.

Limit 1

Untested policies

A comparison says nothing about a policy that is not in the portfolio, such as an age, term, or duration that nobody thought to include.

Limit 2

Rearranged sums

Stopping early, or rearranging the sums so they run faster, adds arithmetic that is not in the original. Results can differ in the last digit, so an exact match is no longer the test.

Limit 3

Different hardware

A GPU may combine a multiplication and an addition into one operation, and at seven digits it keeps fewer digits. Results differ by design.

  • A proof answers the first limit: it covers every policy, under stated assumptions. Section 05 explains how.
  • For the second and third, we also need to know how far rounding can move each result. Section 06 covers this.
05 · Background, not from our models

How mathematicians check proofs by computer

A proof is a chain of steps, each following from the last by the rules of logic. Long proofs are hard for people to check, so mathematicians now write them in a form a computer can check.

Proof checkers

Check every step

A proof checker such as Lean accepts a statement only when every step of its proof follows from the rules. The part that does the checking is small, and many people have studied it closely.

Theorem provers

Search for a proof

A theorem prover such as Z3 looks for a proof without help. When a statement is false, it can give a counterexample. It is a large program, so its answers deserve a second check.

In use

Famous problems

In 2014 a computer-checked proof settled Kepler's 400-year-old conjecture about stacking spheres. In November 2026 the Lean community confirmed that Lean had checked a 17-million-line proof of the Riemann hypothesis, the best-known open problem in mathematics.

  • We use the same tools on much smaller statements: that each formula in the fast model equals the matching formula in the original.
  • Z3 finds each proof, and Lean checks it again.

Riemann hypothesis: joint statement by the Lean and Mathlib communities, 21 November 2026.

05 · Our method

How we use Z3 and Lean

Theorem prover · Z3

Finds proofs and counterexamples

Z3 comes from Microsoft Research. We give it a statement, such as "for every policy, these two formulas are equal". It finds a proof, or returns a counterexample: a specific policy on which the two models disagree. It can also report that it cannot decide.

It is a large program, and its answer depends on that program being correct.

Proof checker · Lean

Checks every step of a proof

We export each statement to Lean, which checks its own proof of it from scratch. We then no longer rely on Z3 being correct.

Lean checked every main statement for all four models. The table two slides on gives the counts.

  • Think of Z3 as a gifted student who solves the problem quickly, and Lean as the examiner who checks every line of the working.
  • When both accept a result, rely on the examiner's check.
05 · Our method · A real example from the term assurance model

Running both models on symbols

To prove two formulas equal, the program replaces each input with a symbol, such as "sum assured", and works through both models' code. If both reduce to the same expression, they are equal for every policy.

The original model, as written 
def claims(t):
    return claim_pp(t) * pols_death(t)

def pols_death(t):
    return pols_if_at(t, "BEF_DECR") * mort_rate_mth(t)
both become
sum assured × policies in force × monthly mortality(age, duration)
so they are equal for every policy
The fast model 
p_death = p_decr * q
claims  = sa * p_death
  • The program reads the original model's own code, so nobody retypes the formulas.
  • A short written description covers the parts it cannot read, such as table lookups and random numbers. A reviewer must check that description; for tables, we test every position.

Slightly simplified. The proof covers every selected result of the model, not just claims: between 20 and 77 results for each model. In the annual model the written description also includes a handwritten reserve formula.

05 · Our method

Proving every month

Part 1 · The first month

Prove that in month 0 every value of the fast model equals the original's, and that it passes the right numbers on to month 1.

Part 2 · Any month, given the month before

Prove that if the numbers passed into a month are right, every value in that month is right, and it passes on the right numbers too.

  • Together these cover month 1, then month 2, and so on to any month: the first domino falls, and each one knocks over the next.
  • The same argument shows that stopping early is safe in exact arithmetic: once no policies remain, every later cashflow is zero.
  • Computer results can still differ where the original later produces an undefined value; in the dynamic lapses stress test this affects 20 rows.

Press → three times. Mathematicians call this "proof by induction". A general result in Lean carries the two parts to every month; connecting each model to that result is a step a reviewer must check.

06 · Rounding

How computers round numbers

Proofs deal with exact numbers. Computers keep a fixed number of digits: about 16 as standard, or about seven on a GPU at reduced precision.

Each result is rounded to fit. The effect is usually tiny, but it grows when two large amounts nearly cancel. Net cashflow is sensitive for this reason.

06 · How far rounding can move an answer

A guaranteed limit on rounding error

We run the fast model once more, carrying every number as a pair: one value known to be below the exact answer, and one above.

Every sum rounds the lower value down and the upper value up, so the exact answer always lies between them. This method is called interval arithmetic.

Each row ends with a narrow range that contains the exact answer. The distance from any computed result to the far end of that range is a guaranteed limit on its error.

Illustrative positions, not to scale. A computed result can lie outside the range; its distance to the far end bounds its error.

Press → twice. The positions are for illustration, not to scale. The range is typically about a millionth of a millionth of the value wide. Results at seven digits fall well outside it. The guarantee holds for the prepared inputs, provided the interval program is correct, and the check reports any row it cannot bound.

07 · Choosing a level of optimisation

Choosing a level of optimisation

Is run time a problem?No: change nothing, or vectorise. Speed is not free.
Must every figure match the current model exactly?Yes: compile, and use all processor cores. On the three monthly tests this ran about 106 to 424 times as fast as lifelib's version, on ordinary hardware. Recorded values match on the test portfolios; present values match when added in the original order.
Still not fast enough?Restructure: stop early and rearrange sums. This is up to about twice as fast again. A proof shows equality in exact arithmetic under stated assumptions; rounding checks cover the rest.
Still too slow after that?Only then consider a graphics processor. Use 16 digits if the device is built for it. For seven digits, set an acceptable error for each reported output and check it on the intended workload, including totals, percentiles, and ratios.

We recommend vectorising, compilation, and parallel cores by default. They give most of the speed with the simplest evidence. Early exit helps the largest runs. Consider a GPU only if a run is still too slow after that.

08 · What is new

What is new

Some platforms run analyst-readable code on GPUs. Our route is different: an AI coding agent rewrites the model as low-level code for ordinary processor cores, and mathematical proofs of equivalence support model validation.

01

The original model is the reference

The existing model runs unchanged, and the checks compare the fast version with it.

02

Individual values are compared

The fast model must agree on each recorded amount in each period, and planted errors measure how strong that check is.

03

Proof for every policy

Proofs show equality in exact arithmetic for any policy under stated assumptions, including the shortcuts that make the fast versions fast.

04

Proofs checked separately

Lean checks a separate proof of each statement, which removes the reliance on Z3.

05

Guaranteed error bounds

A separate check bounds each row's rounding error for runs on a graphics processor.

06

Built for AI-assisted conversion

A person or an AI coding agent can write the fast model, following a written procedure. The checks assess the result. A reviewer still checks the written description and assumptions.

We do not know how commercial platforms work inside, and some may do parts of this.

lifelib is an open source library of actuarial models written in Python. Its models are smaller and simpler than real production models. Because they are public, anyone can repeat every figure here.

The timing computer is one NVIDIA DGX Spark, a desktop-sized computer with 20 processor cores and a GB10 graphics processor that share 128 GB of memory. All times come from one sequence of runs.

08 · Scope

Optimisations we did not try

We changed how each model runs, not what it calculates for each row. These other ways to save time are untested.

Remove duplicate rows

Rows with identical inputs need only one projection. Results stay exact. Our term assurance and traditional life timing workloads repeat lifelib's sample policies, so this alone would make them almost free. Read those timings as throughput for a portfolio of that size.

Share work across scenarios

In the savings model, mortality and lapses do not depend on the scenario, so the policies in force could be worked out once for each policy. Results stay exact. This does not apply when lapses depend on the scenario.

Group similar policies

Actuaries often replace many policies with fewer representative ones. This is an approximation, so it falls outside our rule: each change keeps results exact or has a proven error bound.

Smarter seven-digit sums

A running total can carry a correction for the digits it loses. We tested a simpler form, mixed precision, and it gained little. Carrying the account value in 16 digits might do better.

Several machines

Rows do not affect each other, so a run can split across machines. We tested single machines only.

The first two keep results exact and could be large gains. They are the obvious next steps.

08 · Limits

Limitations

  • These are open source lifelib models, not production models. Production models have management actions, many more products, and policies that affect each other. Nothing here shows the effort or the gains for those.
  • The proofs concern a written description of the original model. Written assumptions replace the parts that cannot be run on symbols. We test these assumptions but do not prove them. In one model, a person wrote the reserve formula by hand. Someone must review the description like any other model documentation.
  • The checks aim to detect honest mistakes during conversion, by a person or an AI agent. They do not protect against someone who deliberately tries to get a wrong model accepted. Other conversion errors may remain.
  • Input preparation, such as reading policy data and building tables, has comparison tests but no proof.
  • Error bounds apply to the rows in a checking run, after the run. They say nothing about rows that were not checked.
  • Timings come from one computer and measure the projection only. Graphics processors vary widely in how fast they do 16-digit sums.
